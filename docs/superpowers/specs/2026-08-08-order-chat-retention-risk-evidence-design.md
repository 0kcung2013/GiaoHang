# Order Chat, Retention, and Risk Evidence Design

## Status

Approved in conversation on 2026-08-08. This document defines the design only; it does not authorize or apply database changes.

## Objective

Replace the current transient Supabase Broadcast demo with durable, order-scoped chat. Messages are stored in PostgreSQL, delivered through Supabase Realtime, searchable from their order, and automatically deleted 14 days after the order is completed or cancelled. Support can preserve selected messages as immutable evidence in an existing risk report.

## Scope

The first implementation includes:

- Customer and assigned driver text messages.
- Large quick-reply buttons already used by the driver workflow.
- Durable message history grouped by `order_id`.
- Supabase Realtime delivery while either participant is online.
- Unread counts and read state per participant.
- Read-only chat for 14 days after an order reaches a terminal status.
- Automatic deletion after the retention window.
- Manual attachment of selected messages to `risk_reports`.
- RLS and database-level authorization tests.

The first implementation excludes:

- AI risk classification or automatic risk-report creation.
- Push notifications while the application is closed.
- Attachments, images, audio, typing indicators, and online presence.
- Message editing, withdrawal, and participant deletion.
- Full-text search across every order.

## Architectural Decision

PostgreSQL is the source of truth. A message is saved before it is considered sent. Clients subscribe to Postgres Changes for the active `order_id`; Realtime is a delivery mechanism, not the durable store.

```text
Customer or driver
        |
        | INSERT message
        v
public.order_messages
        |
        | Supabase Realtime Postgres Changes
        +------------------+-------------------+
        |                  |                   |
        v                  v                   v
Chat message list   Unread indicator   Risk evidence selection
```

Every chat entry point receives an `order_id`. The customer tracking screen, order history/detail screen, and driver navigation screen always open the conversation for that order only.

## Data Model

### `public.order_messages`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key; generated by the database |
| `order_id` | `uuid` | Required FK to `orders(id)` with restricted order deletion |
| `sender_id` | `uuid` | Required FK to `users(id)`; must equal `auth.uid()` on insert |
| `message_type` | `text` | `text`, `quick_reply`, or `system` |
| `body` | `text` | Trimmed length from 1 through 1,000 characters |
| `client_message_id` | `uuid` | Required idempotency key generated by the client |
| `created_at` | `timestamptz` | Database timestamp; immutable |
| `expires_at` | `timestamptz` | Null while active; terminal transition sets it to `closed_at + 14 days` |

The persisted row does not accept a client-provided sender role. The role is derived from whether `sender_id` matches `orders.customer_id` or the assigned `orders.driver_id`. This prevents role spoofing.

Constraints and indexes:

- Unique `(sender_id, client_message_id)` to make retries idempotent.
- Index `(order_id, created_at desc, id desc)` for order history and cursor pagination.
- Partial index on `(expires_at)` where `expires_at is not null` for retention cleanup.
- No `updated_at` or `deleted_at`; participant messages are immutable.

### `public.order_message_reads`

| Column | Type | Rules |
| --- | --- | --- |
| `order_id` | `uuid` | Required FK to `orders(id)` |
| `user_id` | `uuid` | Required FK to `users(id)` |
| `last_read_message_id` | `uuid` | Nullable FK to `order_messages(id)` using `ON DELETE SET NULL` |
| `last_read_at` | `timestamptz` | Last time the participant opened or read the conversation |

The primary key is `(order_id, user_id)`. A user can update only their own read row and only when they participate in the order.

### `public.risk_report_message_evidence`

| Column | Type | Rules |
| --- | --- | --- |
| `risk_report_id` | `uuid` | Required FK to `risk_reports(id)` |
| `source_message_id` | `uuid` | Nullable FK to `order_messages(id)` using `ON DELETE SET NULL` |
| `order_id` | `uuid` | Required snapshot of the source order |
| `sender_id` | `uuid` | Nullable source sender identity |
| `message_type` | `text` | Snapshot of the source message type |
| `body_snapshot` | `text` | Immutable source content at attachment time |
| `sent_at_snapshot` | `timestamptz` | Immutable original send time |
| `added_by` | `uuid` | Support or Admin actor |
| `created_at` | `timestamptz` | Evidence attachment time |

The primary or unique key is `(risk_report_id, source_message_id)` while the source exists. Evidence insertion must verify that the risk report and message have the same `order_id`. Evidence rows are immutable and remain after normal chat retention deletes the source message.

## Authorization and RLS

RLS is enabled on all three public tables. `anon` receives no privileges.
`authenticated` receives only the table privileges required by the policies:
message `SELECT`/`INSERT`, read-state `SELECT`/`INSERT`/`UPDATE`, and staff-only
evidence `SELECT`/`INSERT`. No client role receives message `UPDATE` or `DELETE`.

### Message read

Authenticated users may read an order message only when one of these conditions holds:

- The caller is the order's `customer_id`.
- The caller is the order's assigned `driver_id`.
- The caller is Support or Admin and an existing risk report references the same order.

### Message insert

The database accepts a message only when:

- `sender_id = (select auth.uid())`.
- The caller is the customer or assigned driver of the referenced order.
- The order status is `assigned`, `picking_up`, or `delivering`.
- The body and message type satisfy constraints.
- Participant inserts may use `text` or `quick_reply`; only trusted database
  code may create a `system` message.

Customer and Driver receive no `UPDATE` or `DELETE` privilege on `order_messages`.

### Read state and risk evidence

- Participants may select and upsert only their own `order_message_reads` row.
- Only Support and Admin may create or read risk evidence.
- Risk-evidence writes go through a narrowly scoped database command or protected trigger that validates actor role and matching `order_id`.
- Any privileged function uses an empty `search_path`, explicit `auth.uid()` checks, and revoked `PUBLIC`/`anon` execution.

## Message Flow

### Sending

1. The client creates a UUID `client_message_id`.
2. The UI renders a local pending bubble.
3. The application inserts the message into PostgreSQL.
4. RLS and constraints validate participation, status, identity, and content.
5. The returned database row replaces the pending bubble.
6. Realtime delivers the inserted row to the other participant.
7. Clients deduplicate by database `id`; retries deduplicate through the client key.

### Receiving

- When chat is open, an allowed Realtime insert is added to the current list.
- When tracking or navigation is open but chat is closed, the UI shows a floating notification and increments the unread badge.
- Opening chat fetches persisted history before subscribing, preventing a gap between offline history and new events.
- Reconnection performs a catch-up fetch after the latest known `(created_at, id)` cursor.

### Reading

Opening or viewing the latest message upserts `last_read_at` and `last_read_message_id`. The unread count includes messages in the order newer than the user's read cursor and excludes messages sent by that user.

## Order-Scoped Discovery and UI

- The tracking card and driver navigation open chat for the active order.
- A completed or cancelled order detail shows a `Tin nhắn` action for 14 days.
- Terminal-order chat is read-only; the composer and quick replies are hidden.
- After expiration, the order detail displays `Lịch sử trò chuyện của đơn này đã hết hạn`.
- Operations Web opens chat from an order or a risk-report detail. It never displays an unscoped global conversation list in the first version.

## Risk Evidence Flow

1. Support creates or opens a risk report for an order.
2. The risk-report detail shows the still-retained chat for that same order.
3. Support selects one or more messages and chooses `Thêm làm bằng chứng`.
4. The database copies the source fields into immutable evidence rows and validates the order match.
5. The command updates `risk_reports.updated_at` and `updated_by` in the same
   transaction, so the existing audit trigger records a supported `updated`
   event. The immutable evidence row records who attached the message and when.
6. Normal retention later deletes the source message, sets `source_message_id` to null, and leaves the evidence snapshot intact.

The system does not infer risk from message text and does not automatically create reports. AI classification remains a future extension.

## Retention and Cleanup

When an order first transitions to `delivered` or `cancelled`, a private database trigger sets `expires_at` on all of that order's messages to exactly 14 days after the terminal transition time. Subsequent unrelated updates must not extend the deadline.

A Supabase Cron job runs once per day and invokes a private cleanup function. The function deletes expired messages in bounded batches so it does not hold long locks. It is not executable by client roles. The job's run history provides an operational audit of cleanup success or failure.

The cleanup function removes the corresponding `order_message_reads` rows after
the order's final retained message is deleted, preventing stale unread state.

For the demo dataset, daily cleanup is sufficient. Production-scale partitioning is explicitly out of scope.

## Error Handling

- Offline or timeout: retain a failed/pending bubble with a retry action and reuse the same client key.
- Authorization failure: remove the pending bubble and show that chat is unavailable for the order.
- Duplicate insert: fetch the existing row for the client key rather than creating another message.
- Realtime disconnect: show a reconnecting state, resubscribe, then catch up from PostgreSQL.
- Expired conversation: close the composer, remove unread state, and show the expiration message.
- Evidence attachment after source expiration: reject with a clear message because no source chat remains to verify.
- Cron failure: retain messages until a later successful run; never delete early on a partial error.

## Testing and Acceptance Criteria

### Database tests

- The order customer and assigned driver can read the same order's messages.
- An unrelated authenticated user cannot read or insert messages even when they know `order_id`.
- A driver cannot access an order assigned to another driver.
- Clients cannot spoof `sender_id`, update a message, or delete a message.
- Retrying the same client key produces one durable message.
- Terminal transition sets one stable 14-day deadline for every order message.
- Cleanup removes expired messages but preserves evidence snapshots.
- Support cannot attach a message to a risk report for another order.

### Flutter tests

- Opening chat for order A never renders order B messages.
- Persisted history loads before new Realtime events are merged.
- Incoming messages update the open sheet and the closed-chat unread badge.
- Duplicate Realtime events render once.
- Completed/cancelled chat is read-only before expiration.
- Expired chat shows the correct empty state.
- Quick replies remain usable on a small landscape phone with large text.

### Operations Web tests

- Support can view chat only after opening a risk report for that order.
- Selected messages create immutable evidence rows.
- Evidence remains visible after source-message cleanup.
- Admin and Support authorization is enforced independently of UI visibility.

## Reporting Narrative

The graduation report can describe this subsystem as an order-scoped, durable realtime chat with database-enforced authorization, idempotent delivery, bounded retention, and manual preservation of selected evidence for incident investigation. AI message-risk classification, push notifications, and attachments are future work rather than claims of the demo.
